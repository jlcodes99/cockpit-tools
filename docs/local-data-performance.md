# 本地数据查询与迁移实现说明

规范见 [查询字段与无感数据迁移规则](query-and-migration-rules.md)。本文记录此次性能治理的实现边界与回归检查点，不是发布操作指南。

## 查询路径

| 场景 | 新读取路径 | 写入与历史处理 |
| --- | --- | --- |
| Kiro / Windsurf 账号列表 | 只读取账号，不在列表调用中去重 | 后台身份快照回填、按身份分桶查找重复；版本完成后停止去重 |
| Kiro / Windsurf / Trae 添加、更新匹配 | 优先读取索引中的版本化身份快照，仅未回填记录回退读详情 | 所有宿主详情保存入口先失效变化的身份投影，再保存详情与摘要；后台 CAS 写回不能覆盖更新、删除 |
| 请求日志会话筛选 | 可索引的 `effective_session_id` 映射 → request ID 索引 | 诊断写入、更新、删除由同事务触发器维护；历史每批最多 32 条；未完成时只扫描受限保留的诊断表，不逐条探测全部日志 |
| 请求日志实例筛选 | 等值匹配实例 ID | 使用现有实例/时间索引；账号和 API Key 的精确 ID 参数与自由文本搜索参数分离 |
| Codex 会话用量同步 | 文件未变化跳过；追加从字节检查点继续 | 持久化模型、累计 token 高水位、快照签名、事件编号、分叉匹配位置和未完整写入的尾部状态 |
| 父会话回放去重 | 宿主库中按文件、代次、签名、行号查询 | 父 JSONL 分批解析，不保留全历史内存数组；官方日志只读 |
| API / 会话用量统计 | UTC 分钟汇总 + 时间范围边界明细 | 新增、更新、历史价格重算、删除均由源表触发器增减；成员表避免回填与实时写入重复累计 |

会话 ID 仍遵守“已采集 thread ID 优先，否则 session ID”规则；未采集的数据保持未知。诊断清理会同步清理映射，保留原有诊断保留期语义。

## 资源控制

- 自动维护共享单工作线程与资源许可，队列最多 16 个不同任务，同一任务去重。
- 默认每批最多 32 条、2 MiB 输入，协作式 CPU 时间预算 25ms，批次间至少休息 150ms；SQL 回填另有执行中断预算。
- 锁争用不等待：`try_lock` 失败先让路；SQLite 后台锁等待为 10ms。文件读取/解密在批次内执行，不能保证单次系统调用的墙钟耗时小于预算，但不在主线程或异步执行线程同步等待。
- 账号详情后台加密先生成密文，再尝试取得文件锁并校验原文件摘要。前台保存最多等待该锁 40ms，避免短暂后台写回造成授权或编辑失败。
- 账号详情超出单条维护字节预算时保留原文件，不伪造身份，不清空账号；记录维护失败供后续排查。
- 分批失败最多连续重试 5 次并退避；后续访问可重新调度，持久化游标或记录版本保留已完成进度。
- 查询并发最多 2 个，前端统计修订采样与输入防抖抑制密集重查。运行中的物理查询仍持有并发许可，调用方离开页面不会释放许可后启动无限新任务。

资源预算是限制并发、输入规模与持续占用的机制，不是对所有硬件承诺固定 CPU 百分比或零磁盘开销。不得为了追求升级速度扩大批次或取消批间让步。

## 数据安全与一致性

- 身份索引不存明文凭据；只保存平台身份字段和凭据摘要。旧数据缺字段只针对未回填记录兼容，完成后直接使用新快照。
- 自动去重先保存合并结果和重复详情的原格式备份，再更新索引，最后按原文件哈希清理重复详情；加密文件的备份仍为密文，历史明文文件不会被冒称为加密备份。保留已绑定账号 ID；两个账号都被实例绑定时不自动删除其中任一个。
- 已提交解析事件与解析检查点在同一事务中更新；半条 JSONL 不推进检查点。超长非用量消息分段跳过，超长用量记录显式报错，不静默生成错误计费。
- 文件被截断或重写时，旧数值快照分批备份，重建期间仍供报表查询。替换解析全部完成才切换可见结果；中断后保留旧结果并从持久化进度恢复。
- 汇总未完成时只合并尚未入桶的源记录，使用同一个读事务快照，避免迁移推进与查询交错导致漏计/重复。已完成后移除该兼容扫描。
- 汇总按 UTC 分钟存储，按当前本地时区展示；时区变化不需重新清洗所有明细。时间范围两端不足完整分钟的部分继续精确读取明细。
- 价格变更维护汇总金额；消费预算结算是独立业务数据，不因历史价格重算而改变。

## 复审与验证清单

1. 旧摘要缺字段、身份冲突、同邮箱不同用户、不同 API Key 与不同 Trae 平台。
2. 一万个不同身份的分批扫描不产生两两比较；记录版本与索引修订变化使扫描重新校验。
3. 回填期间更新、删除、源文件变化，CAS 不能覆盖新版本或复活已删除文件。
4. 会话筛选查询计划使用会话映射索引和 request ID 索引，不出现逐日志行的关联子查询。
5. JSONL 追加、未写完尾部、跨批次累计用量、分叉签名跳跃匹配及进程重启恢复。
6. 汇总回填与实时更新交错、金额重算、清空、ID 复用、时间边界、事务回滚及文件重写的旧快照保留。
7. 仅使用临时目录和合成数据进行代码级验证，不启动 GUI、不读写真实账号库、不执行正式数据清洗脚本。

## 存储迁移盘点

下表区分应用日常读写与升级输入。账号凭据详情和官方客户端目录沿用各平台原有落盘规则。

| 数据 | 日常读写来源 | 升级时的处理 |
| --- | --- | --- |
| 账号摘要与索引内的当前账号 | Antigravity 使用 `antigravity_accounts.sqlite`，其他平台使用各自的索引 SQLite。桌面和 CLI 的共享账号模块读取同一存储 | 分批从旧索引导入，保留旧文件 |
| 账号详情与凭据 | Cockpit 管理的账号详情使用本机密钥加密文件，桌面与共享核心沿用同一格式 | 兼容读取旧明文详情，保存时加密主文件与新备份 |
| 账号分组与独立当前账号 | 宿主使用 `account_groups.sqlite` 和 `provider_current_accounts.sqlite` | 分组按平台保存成员顺序，当前账号清除有独立记录 |
| 实例绑定与启动设置 | 桌面和 CLI 的共享实例存储使用 `instance_registry.sqlite` | 旧登记文件保留 |
| 2FA 与 APIKEY.FUN | 宿主使用 `mfa_vault.sqlite` 和 `apikey_fun_vault.json`，凭据均加密 | 旧 WebView 作为升级输入。两项均有本机加密恢复备份 |
| 唤醒、签到、切号和重置卡执行记录 | 调度器和历史页使用 `wakeup_history.sqlite`、`checkin_history.sqlite`、`switch_history.sqlite`、`codex_reset_journal.sqlite` 等按用途划分的库 | 旧数据按模块后台导入 |
| 调度配置与运行进度 | 签到进度使用 `checkin_state.sqlite`，唤醒状态使用 `antigravity_wakeup_state.sqlite` 和 `codex_wakeup_state.sqlite`。配置规则按模块保存 | 已迁移的旧规则与进度留作升级输入 |
| 界面与通用配置 | 已迁移的界面偏好使用 `ui_preferences.json`，通用设置使用 Rust 管理的 `config.json` | 升级先读可用旧值，随后以后端配置为准。Codex API 服务日志列、分页、地址类型、统计时间范围、代理导入协议、唤醒模型和各平台实例排序也纳入本地偏好 |

平台布局启动时可先显示旧缓存。后台核对本地布局与旧缓存版本，旧缓存有较新的未落盘布局时会补写一次。随后编辑和配置恢复只写 `ui_preferences.json`，以修订号防止其他窗口覆盖较新版本。配置备份保留旧版的 `platform_layout_config` 字段。备份省略此字段时保留当前布局，显式清空则写入本地状态，避免再次读回旧缓存。

Codex 模型供应商的自定义顺序和启用状态保存到本地偏好。供应商列表刷新只更新显示顺序，拖动结束后才保存改动。Codex 实例页、会话管理和供应商绑定选择共用本地实例排序偏好。

Antigravity 和 Codex 的自定义账号排序开关保存在 `ui_preferences.json`，顺序保存在 `user_memory.json`。升级时旧缓存只补本地缺少的项目，已有关闭状态和空列表均保留。Antigravity 的实例账号选择器使用账号页的排序偏好。Codex 的配置备份使用账号身份匹配排序，恢复时重新解析本机账号 ID。

悬浮卡最后的平台和打砖块数据保存在 `ui_preferences.json`，打砖块历史保留最近 200 条。界面首屏可以使用上次语言缓存，Rust 的 `config.json` 是语言配置和备份的来源。旧备份只有 `app_language` 时，导入把该值写入通用配置。

账号首屏缓存仅用于显示。Antigravity、Codex 和平台共享账号缓存写入时去除凭据字段，打开旧缓存时也会转换为可重建的展示数据。旧缓存写回前会再次核对原值，避免覆盖已经从宿主更新的缓存。Codex 账号备注、API Key 编辑和启动预览、Antigravity 账号备注、Claude 网关编辑在需要时后台读取本地账号。弹框先显示读取进度，失败后可以在原处重试，关闭后丢弃迟到的表单结果。超时重试会复用尚在进行的本地读取。切号继续由 Rust 执行。

WebView 仍保存首屏页面、语言提示、账号和实例摘要、可重新查询的用量，以及运行中导入的会话标识。这些值可以重新生成或随会话失效。桌面端和 CLI 各自读写同一套 Cockpit 数据时，官方客户端的凭据注入路径及文件格式沿用原实现。

## 2FA 恢复检查点

旧版的故障机制可以追溯到 2026 年 5 月 20 日的 v0.24.0（`d27740f90`）。读取 WebView 出错时返回空数组，页面挂载后会将这个数组写回。v1.3.80 的 2FA 页面改动和 v1.3.81 都保留了这一行为，两个正式版本的 macOS 应用标识相同。仓库历史能确认写回空列表的路径，具体安装中首次读取失败的原因仍需当时的升级和 WebView 记录才能确定。

应用以数据目录中的 `mfa_vault.sqlite` 为准。已保存密钥和查询历史各自记录迁移来源、偏移、完成状态和修订号。两份列表迁移完成后，后台创建或检查同目录中的 `mfa_vault.recovery.sqlite`。记录和校验清单均使用本机密钥加密，检查点依赖原数据目录的 `secure-account-storage.key`。

检查点使用 SQLite 一致性快照，每步最多复制 32 页。复制后逐批校验记录密文、身份和时间，并将两份列表的进度、记录数和内容摘要纳入认证清单。校验每批最多 32 条，达到字节或时间预算即让出资源。发布前核对源库修订号，确认数据未变化才替换上一份检查点。复制中断会留下可清理的暂存文件，下一次运行重新复制并保留上一份已发布检查点。

主库文件缺失且本机有检查点时，2FA 页面提供「恢复本机备份」。应用先校验暂存副本，再将其发布为主库，恢复已保存密钥、查询历史和迁移进度。如果主库已存在，或仍有该主库的 SQLite 日志文件，原文件会保留。恢复取自最近成功写入的检查点，其后的更改可能不在其中。

普通配置备份使用 `cockpit-tools.data-transfer` v1 的 `config.verification_records` 和 `config.verification_history`，两项都从当前密钥库读取。只有迁移完成的列表才写入备份。迁移期间省略尚未完整的字段，恢复时保留对应列表，避免部分记录覆盖完整密钥库。v1.3.81 的导入器也读取这两个字段。加密密钥留在原数据目录，和检查点分别保存。

托管备份完成后的自动轮转会保留符合恢复命名规则的旧配置备份及其 ZIP，直到两份列表迁移完成且当前修订的本机检查点可验证。必要时，轮转先在后台创建或刷新检查点。两份列表均已迁移为空且从未生成密钥时可以正常清理。未包含已保存密钥的新托管备份带有 `_mfa-pending` 文件名后缀，仍可导入其他配置，也不会占用自动恢复的 32 份候选窗口。显式清理和逐个删除仍由用户操作。

代码级验证使用 `npm run test:rust -- mfa_vault_store`，在临时目录中覆盖多批复制、暂存中断、篡改检测、原库校验失败、主动清空后的备份更新、主库缺失后恢复和并发文件保护。

配置备份兼容性验证使用当前配置导出器生成合成备份，再在隔离的内存存储中执行 v1.3.81 的配置导入器。已验证两份 2FA 列表分别写入旧版保存记录和查询历史字段。

## APIKEY.FUN 密钥备份与导出格式

应用以数据目录中的 `apikey_fun_vault.json` 为准。迁移、保存和清空后的状态由后台读取、认证并复制到同目录的 `apikey_fun_vault.recovery.json`。同一目录的备份任务去重，单次处理最多 2 MiB。备份使用本机加密密钥，清空后的备份仍是一份有效的空列表。

主文件缺失且已有本机备份时，密钥管理页提供「恢复本机备份」。恢复先验证密文，再创建主文件，保留已经存在的主文件。恢复内容以最近成功写入的备份为准。

「导出明文 JSON」读取当前密钥库，生成 v1.3.81 所用的密钥数组格式，包含别名、使用时间和附加状态。已用合成密钥验证 v1.3.81 的原始读取函数能保留该数组及附加字段。v1.3.81 从 WebView 的 `apikey_fun_managed_keys` 读取数据，页面没有文件批量导入入口。使用旧版页面时，可以从导出文件取出密钥逐条保存，旧版会重新生成使用时间等元数据。此导出与本机加密备份分别保存。

## 执行历史的自动迁移

桌面端切号、唤醒、唤醒验证和签到历史直接返回 SQLite 已提交记录。剩余旧数据由后台从检查点继续导入，页面仅在迁移期间刷新已提交的结果。旧源读取失败时保留已有记录并提供重试。唤醒验证中已显示的批次可直接删除，删除记录同时阻止后台重新导入。切号历史的 CLI 读取仍可从检查点合并旧文件剩余部分，同日签到合并也从检查点查找尚未导入的日期。迁移途中发现旧文件被替换时，会报告源文件变化并保留当前记录与检查点。

旧文件作为迁移输入留在原位。中断或失败时，应用保留已提交的数据和迁移检查点，后续继续处理。
